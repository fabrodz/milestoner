# M05 - The state lock cannot be broken by the process that just took it

## Objective

`withStateLock` actually serialises a read-modify-write across processes. Today it does not: under
contention a second process deletes a lock that a first has legitimately just acquired, both enter
the critical section, and one update is lost. That is the exact failure D-022 exists to prevent.

## Context

- `src/lock.ts`. `openSync(file, "wx")` is the atomic test-and-set, but it **creates the file
  empty**; the holder payload is written on the next statement. Between those two lines the lock
  exists with no contents.
- `breakIfStale()`'s `catch` treats "unreadable, empty or half-written" as nothing worth waiting for
  and calls `rmSync(file, { force: true })`. For the empty case the reasoning is inverted: an empty
  lock file is the signature of a lock acquired microseconds ago, which is the one that most needs
  respecting.
- Reproduced deterministically, not inferred: open the file `wx`, run `breakIfStale` from the
  contender's position, and the lock is gone while the first holder still believes it holds it. A
  third process then takes `wx` freely.
- Observed in CI as `not ok 36 - concurrent registration from several processes loses no entry` on
  `ubuntu-latest / node 20`, run 32420272395, with `run-1` lost out of six. Green on node 22 and 24
  in the same run, and green on Windows for the whole v0.5 run, so it is a race that the suite
  happens not to lose rather than a platform difference. The window exists on Windows too.
- There is a second, harder path to the same end: when `WAIT_MS` (5s) expires the code removes
  another process's lock and runs `fn()` unlocked. That is deliberate and commented, but it is a
  second way two processes end up in the critical section, and it should be revisited now rather
  than left beside a fix for the first one.
- `src/lock.test.ts` and `src/registry.test.ts` are the tests that cover this. Neither caught it.
- Out of scope: the panel, the runner, the registry's own logic, anything outside locking and the
  tests that cover it.

## Decisions to make inside this milestone, and record

- **How the lock becomes visible with its payload already in it.** `linkSync(tmp, lockfile)` fails
  when the destination exists, is atomic, and the temp file can carry the pid before the link is
  made. Choose that or something better, say why, and say what happens on a filesystem where hard
  links are unavailable.
- **What `breakIfStale` does with a lock it cannot read.** It must not delete it on sight. A grace
  window keyed on when the unreadable file was first seen is the obvious answer; say how that is
  tracked, given the contender is a different process on each attempt.
- **Whether the `WAIT_MS` fallback keeps running `fn()` unlocked.** It trades a lost update for a
  stuck run and was chosen deliberately. Revisit it with the rest of the mechanism in view and
  record the answer either way, including "unchanged, and here is why".

## Tasks

1. Make the lock file carry its holder from the instant it exists.
2. Stop `breakIfStale` from deleting an unreadable lock immediately.
3. Write a regression test that fails against today's lock and passes after. It must drive the
   window explicitly rather than spawning contenders and hoping one loses; a test that only fails
   sometimes is what let this through.
4. Keep the existing concurrent tests, and make them exercise enough contention to have caught this.
5. Re-verify on all three platforms.
