# M01 - Plugin manifest and the supervisor skill as a plugin component

## Objective

At the end of this milestone the repository *is* a valid Claude Code plugin. `claude plugin
validate . --strict` exits 0, and the supervisor skill that `dogwatch skill install` writes is also
shipped as a plugin component, from the same source of truth, with a test that fails if the two
ever drift.

Nothing about the CLI changes. This milestone adds a second distribution channel beside npm; it
does not move the first one.

## Context

- `src/templates/skill.ts` holds `SKILL_NAME` and `SKILL_TEMPLATE`, the full text of the supervisor
  skill. `src/commands/skill.ts` writes it to `.claude/skills/<name>/SKILL.md`.
- `docs/DECISIONS.md` D-002 sets the distribution split (npm now, plugin in v0.4) and D-010 records
  why the skill is a file the CLI writes rather than a plugin component; you are implementing the
  half of D-002 that was deferred, so D-010's "for now" ends here. Both stay true: the CLI keeps
  writing the file.
- The manifest schema, verified against the installed Claude Code CLI: `.claude-plugin/plugin.json`
  with `name`, `description`, `version`, `author` (an object with `name`), `license`, `keywords`.
  Run `claude plugin validate --help` and inspect a real installed plugin under
  `~/.claude/plugins/` if you need to confirm a field.
- Out of scope: slash commands (M02), the marketplace manifest (M03), CI and release plumbing
  (M04). Do not do their work early.

## Tasks

1. Add `.claude-plugin/plugin.json` at the repository root. `name` is `dogwatch`, `version` matches
   `package.json` exactly, `description` says what the plugin gives a Claude Code user, and the
   metadata (`author`, `license`, `keywords`, homepage/repository if the validator accepts them)
   agrees with `package.json`.
2. Ship the supervisor skill as a plugin component at `skills/dogwatch-supervisor/SKILL.md`,
   generated from `SKILL_TEMPLATE` so the text exists once. Add a build or prepare step that
   regenerates it, wired into an existing npm script rather than left as a manual step.
3. Add a test that reads the shipped `skills/dogwatch-supervisor/SKILL.md` and asserts it is
   byte-identical to `SKILL_TEMPLATE`. This is the drift guard; it must fail if someone edits one
   and not the other. Prove it fails by breaking it deliberately, then restore.
4. Make sure `npm pack` still ships only what `package.json`'s `files` list intends. Decide whether
   the plugin files belong in the npm tarball and log the decision.
5. Add a `.claude-plugin` note to the `## Layout` section of `README.md` only if the section covers
   repository layout; if it only covers `.dogwatch/`, leave it alone and save the README work for
   M03, which owns the install docs.

## Acceptance criteria

- **AC1** - `claude plugin validate . --strict` exits 0. (evidence: the command's output and exit
  code, captured in `.dogwatch/evidence/M01-validate.txt`)
- **AC2** - `skills/dogwatch-supervisor/SKILL.md` exists and is byte-identical to the text
  `dogwatch skill install --print` emits. (evidence: a diff producing no output, captured in
  `.dogwatch/evidence/M01-skill-diff.txt`)
- **AC3** - A test guards that identity, and it genuinely fails when the two diverge. (evidence:
  the test name, the pass count from `.dogwatch/evidence/M01-test.txt`, and a line in the execution
  log recording the deliberate-break check)
- **AC4** - `plugin.json`'s `version` equals `package.json`'s `version`. (evidence: both values
  quoted in the execution log)
- **AC5** - `npm run typecheck`, `npm test` and `npm run build` all exit 0. (evidence: the test
  counts in `.dogwatch/evidence/M01-test.txt`)

## Exit

- All acceptance criteria evidenced.
- Build clean, test suite green.
- Committed and tagged `v04-plugin/M01`.
- `.dogwatch/result.json` written with `status: "done"` and one evidence line per criterion.
